# citrate-comms QA sweep — 2026-08-01

Fourth app in the Commissary cadence.

**Verdict: three defects, and all three are the same shape — a control that was
correct in mechanism and unenforced in fact.** Nothing here is a broken design. Each
is a guarantee the code genuinely intends, stated in a way that outran what it
checked.

---

## 1. The defects

### C-1 — The PII guard could not see a name

`schema.no-pii.test.ts` exists to force "a deliberate decision ... rather than a
silent plaintext leak." Its sensitive-segment list was `{body, text, secret, note,
notes}`, so **`contacts.name` sat in cleartext directly beside `contacts.email_enc`,
which IS encrypted**, with nothing recording that as a choice. A CRM's most
identifying field slipped the guard designed to catch exactly this.

Second defect in the same file: the allow-list keyed on the **TypeScript property
name**, so one `"email"` entry blessed `members.email`, `invites.email`, and every
future `X.email`. An exemption granted to one table silently applied to all.

Fixed by widening the segment list and re-keying to `table.column` — which required
parsing per table rather than per line. The guard now demands each sensitive column
be **encrypted or a recorded decision**; 25 carry a stated reason.

**Proof it now bites: adding a cleartext `contacts.phone` fails the new guard and
passes the old one entirely.**

### C-2 — Server-blindness was verified on the invocation, not the artifact

The relay depends on `comms-core` with `default-features = false, features =
["store"]`, so the MLS engine is not compiled in. Real mechanism, well chosen. But
Cargo unifies features across a build:

| Build | OpenMLS symbols in `comms-relay` |
|---|---|
| `cargo build --workspace` | **39** |
| `cargo build -p comms-relay` | **0** |

Measured, not reasoned about.

**What ships is genuinely blind** — both deploy paths already use `-p comms-relay`,
the relay holds no group secrets, and never calls the engine. This is an overstated
guarantee, not a vulnerability. What was missing was anything *checking*: changing
that line to `--workspace` would have silently shipped the MLS engine inside the
server-blind relay.

`bootstrap-droplet.sh` now inspects the built binary and refuses to install if it
finds OpenMLS. Three doc sites corrected to state the scoping requirement.

### C-3 — An expired sponsorship did not stop the agent

`RoleAssertion.not_after` is expressed by the owner, signed by the owner, and checked
by `verify_role_assertion` — **once**, at `accept_sponsor`. The bridge then stored
`Some(assertion)` and every action asked only `sponsor.is_none()`.

A bridge is a long-running process. **An agent sponsored for an hour kept posting for
as long as that process lived** — days, in a deployment — under a lapsed grant. An
owner bounding an agent's authority in time could not actually do so.

`handle()` already received `now`, so nothing had to be plumbed. The re-check uses
`now >= exp`, matching `verify_role_assertion` exactly — with `>` the bridge and the
verifier would disagree about the instant a grant dies.

## 2. What came out clean

- **Webapp authorization.** Layered correctly: `requireCapability` calls
  `requireMember`; `channels/[id]/*` all use the channel-scoped guard. Of 53 routes,
  the only ones without a workspace guard are `join`, `workspaces` (both pre-workspace,
  using `verifySession`) and `unsubscribe` — which is an HMAC-signed RFC 8058 token,
  verified and fail-closed. **No IDOR surface found.**
- **The agent guardrail.** `AddMember`/`RemoveMember` are hard match arms returning
  `Forbidden` — not runtime checks that can be talked out of a refusal.
- **`relay_persists_only_ciphertext_on_disk`** — a real test, already present, that the
  relay's on-disk store holds no plaintext.
- **The Notify frame schema test** — pins that the advisory frame can never carry
  ciphertext or body.
- **Webapp UI.** No fabricated stat literals, no unconditional liveness indicators, no
  inert controls. The two swallowed catches (CRM field seeding, a channel-create
  follow-up) are secondary and low-severity.

## 3. Open for the owner — eleven cleartext columns

These are recorded in `ALLOWED_CLEARTEXT` as `OWNER DECISION PENDING` so the suite is
green and the state is **visible**, not because the trade-off has been agreed:

`contacts.name`, `contacts.title`, `members.display_name`, `channels.topic`,
`threads.title`, `tasks.title`, `tasks.description`, `agent_threads.title`,
`agent_resources.title`, `documents.name`.

The two worth arguing about:

- **`contacts.name`** — the CRM's most identifying field, in cleartext, while the
  contact's email beside it is encrypted. That asymmetry is hard to defend.
- **`documents.name`** — a filename frequently reveals its contents
  (`Q3-layoffs.xlsx`) while the document body is protected.

Several others genuinely cannot be encrypted — a trusted-tier app has to sort and
search workspace names and pipeline stages server-side. The point of the widened guard
is that this is now a decision on the record rather than an assumption.

## 4. Scope, stated honestly

Swept: all 9 crates structurally, the agent bridge and relay in depth, the webapp
schema layer, all 53 API routes for authorization, and the 22 pages for the
fabrication patterns found elsewhere in this cadence.

**Not swept in depth:** the MLS engine's cryptographic correctness in `comms-core`
(2,532 LOC, 33 tests) and the CRM/PM domain logic. Those want a cryptographer and a
domain review respectively, not a QA pass — and `comms-core` is where a T1 external
audit should start.
